# HID capture - Phase C (rotary encoder) - DECODED

Driven by Claude directly (Binding panel -> click rotary segment -> change Media Button).
KEY INSIGHT: the rotary is NOT a separate subsystem. Each rotary direction/press is just
another **Key ID**, written with the SAME command as the keys.

## Layout observed (Binding panel, Fn0)
- 3 keys: A, B, C (my remaps, confirmed on device)
- Rotary dial: CCW=Volume-, press(center)=Mute, CW=Volume+
- Clicking the CCW segment showed editor "Key ID 5", Key Mode=Media Control, Media Button=Volume+

## Captured write: Key ID 5 -> Play/Pause
```
12 ae 53 3c 00 10 05 01 01 00 00 52 1c 6c 07 dc 05 b8 0b dc 05 00 00 03 00 00 00 0c 00 00 00 03
```
Decode (same frame layout as keys):
```
byte3  = 0x3c   write
byte4-5= 00 10  binding block (SAME as keyboard keys)
byte6  = 0x05   Key ID (this rotary direction)
byte11-12 = 52 1c  config address (0x1c52)
byte13-20 = 6c 07 dc 05 b8 0b dc 05  geometry template (rotary-sized; copy verbatim)
byte23 = 0x03   KeyData CLASS = media/consumer  (vs 0x09 = keyboard usage)
byte27 = 0x0c   value (media button code; Play/Pause = 0x0c in app's media enum)
byte31 = 0x03   mode
```

## The unified binding model (keys + rotary)
A binding = write cmd 0x3c to a Key ID (byte6) with:
  - class byte23: 0x09 = keyboard HID usage, 0x03 = media/consumer button
  - value byte27: the usage/enum code (keyboard: standard HID usage e.g. A=0x04; media: app enum)
  - byte31 mode = 0x03
Copy the per-KeyID template (address + geometry) verbatim, swap class+value, recompute the
16-bit checksum (bytes1-2), send, then save with `12 ca 84 06 00 0d 00 96 72`.
